Qué es y por qué se construye así

El frontend es una capa de presentación pura. No calcula reglas de negocio (el 20 % de inasistencia, los folios, los ámbitos por rol), no traduce errores y no decide permisos de datos: todo eso lo resuelven la base de datos y el backend. La SPA pinta lo que le llega, captura la intención del usuario y la envía. Esa separación es la razón de la mayoría de reglas de esta página: si la lógica vive en un solo sitio, no puede diverger entre capas.

Reglas de arquitectura

Son obligatorias (ver AGENTS.md en la raíz del workspace y AsistenciasUCO-Infra/docs/governance/CONSTITUTION.md). Varias las vigila un script que corre en npm run verify; se indica cuál.

Componentes standalone, OnPush y signals

  • Todo componente es standalone y declara changeDetection: ChangeDetectionStrategy.OnPush. Comprobado el 2026-11-22: los 172 *.component.ts lo declaran.
  • Entradas y salidas con input(), output() y model(). No existe ningún @Input() ni @Output() en src/app.
  • Estado local con signal, derivado con computed y efectos con effect. En el código de producción de src/app (sin pruebas) hay 1205 usos de signal o computed repartidos en 159 archivos y 48 de effect(.
  • Se prohíbe bypassSecurityTrustHtml y similares: en src solo aparece en un comentario que explica que no se usa.

Prohibido el polling

La reactividad llega empujada por SSE o por cambios de signals. No hay ningún setInterval en el código de producción (grep -rn setInterval src/app sin pruebas devuelve cero líneas). Un setTimeout puntual no es polling: por ejemplo, attendance-control.component.ts arma un solo temporizador hasta el instante en que la ventana de asistencia abre o cierra, y lo cancela en onCleanup.

effect((onCleanup) => {
  const delay = msUntilAttendanceWindowChange(this.currentSession(), this.nowMs());
  if (delay === null) return;
  const timer = setTimeout(
    () => this.refrescarVentanaAsistencia(),
    Math.min(delay + 25, MAX_ATTENDANCE_WINDOW_TICK_MS)
  );
  onCleanup(() => clearTimeout(timer));
});

Presentación pura: sin lógica de negocio ni parseo de errores

  • Los errores se clasifican por ApiErrorResponse.code (FORBIDDEN, VALIDATION_ERROR, CONFLICT, etc., en API_ERROR_CODE) o por el status HTTP, nunca por el texto del mensaje.
  • El texto que ve el usuario sale de mensajeUsuario (respuestas exitosas) o de message (errores) del backend. El frontend solo trae textos de respaldo.
  • El estado de una toma, si es editable o hasta cuándo, lo calcula el backend (esEditable, editableHastaUtc en core/models/toma-asistencia.model.ts); la UI no lo recalcula. Tampoco se generan identificadores de negocio en el cliente.
  • check:hu-en-ui falla si la interfaz muestra códigos de historia de usuario (HU más tres dígitos).

Redirecciones de rutas antiguas y precarga

Tras la consolidación de pantallas (decano de 16 a 8, coordinador de 12 a 7) las rutas viejas se conservan solo como redirecciones para no romper marcadores, por ejemplo decano/consolidado-asistencia a decano/seguimiento/consolidado, coordinador/grupos a coordinador/programa/grupos o admin/correos a admin/configuracion/correo. La estrategia PrecargaPorRolStrategy (core/routing) precarga en segundo plano, cuando el navegador queda ocioso, solo las rutas marcadas con data.precargar: true y que correspondan a un rol del usuario.

Además, roleScopeInterceptor espeja en el cliente las reglas por prefijo de SecurityConfig del backend: un GET a un prefijo que el rol no puede usar se corta localmente con un 403, para evitar ruido en red y en logs. El backend sigue siendo la autoridad y nunca se interceptan escrituras.

Renovación, 401 y 403

  • Antes de cada petición a la API, authInterceptor pide getValidAccessToken(30). En modo baseline, si el token expira en menos de 30 s, se dispara una única re-autenticación silenciosa por redirección (baselineRenewalStarted); no hay refresh token.
  • 401 inesperado: handle401 serializa la renovación con shareReplay para que las peticiones concurrentes no provoquen una tormenta de refrescos. Si no hay token nuevo, notifySessionExpired() limpia el estado, avisa a las otras pestañas por BroadcastChannel y navega a /login?returnUrl=....
  • 403: el errorInterceptor muestra el toast UI_ERROR_INTERCEPTOR_001 con el id de correlación; la sesión se conserva.
  • Cierre de sesión: la señal cerrandoSesion tapa la interfaz mientras el navegador sale hacia el logout del PDP; clearSession(true) avisa a las demás pestañas.

Mocks fuera de producción

El simulador mock-backend.interceptor.ts (unas 1300 líneas) se descarga de forma diferida solo cuando una petición ocurre con el modo simulado activo (mock-backend-lazy.interceptor.ts). El build de producción lo elimina del paquete con fileReplacements en angular.json:

  • environment.ts por environment.prod.ts (production = true y useFrontendMocks siempre falso).
  • mock-backend-lazy.interceptor.ts por mocks/prod/mock-backend-lazy.interceptor.prod.ts (pasa todo sin cambios).

Errores: toast global, BYPASS y marcarErrorPresentado

El errorInterceptor decide por ApiErrorResponse.code o por el status, nunca por el texto. Una pantalla que presenta el error de forma local no debe duplicarlo en el toast global. Hay dos mecanismos:

  • BYPASS_GLOBAL_ERROR_TOAST (un HttpContextToken<boolean>): la pantalla lo pone en true en la petición y el interceptor no muestra nada. Lo usan, por ejemplo, group.service.ts, attendance-claim.service.ts y perfil.service.ts.
  • marcarErrorPresentado(error) (TD-120): las utilidades getApiErrorMessage, getApiErrorCode y getApiFieldErrors marcan el error como presentado en un WeakSet. Para 400, 409 y 422, el interceptor espera un turno (setTimeout(…, 0)) y solo muestra el mensaje del backend si ninguna pantalla leyó el error. El propio interceptor lee con leerErrorSinMarcar para no marcarlo él mismo.
// core/interceptors/error.interceptor.ts (resumen)
if (leerErrorSinMarcar(() => getApiErrorCode(error)) === API_ERROR_CODE.FORBIDDEN) {
  if (!bypassGlobalToast) toastService.error(mensajeUi('UI_ERROR_INTERCEPTOR_001'), getErrorCorrelationId(error));
} else if (error?.status >= 500 && !bypassGlobalToast) {
  toastService.error(getApiErrorMessage(error), getErrorCorrelationId(error));
} else if (ESTADOS_DE_NEGOCIO.has(error?.status) && !bypassGlobalToast) {
  // respaldo: si ninguna pantalla lo presentó, se muestra el mensaje del backend
}

Modelos de respuesta y paginación

Los contratos están en core/api/models y reflejan la tupla institucional del backend:

Las tablas grandes consumen endpoints paginados con pagina y tamano y se enlazan con PaginationComponent (app-pagination): recibe totalItems, pageSize, currentPage y totalPages, y emite pageChange y pageSizeChange. El script check:openapi-contract valida el frontend contra la copia byte a byte del OpenAPI golden path del backend (docs/contracts/external/backend/, con su .sha256): falla si la copia no coincide con su firma, si se llama con un método que el contrato no define o si un DTO no conforma su esquema.

Tiempo real con SSE

Hay una capa en tres piezas, de modo que las pantallas nunca conocen fetch, cabeceras ni reintentos:

  1. RealtimeService (core/realtime/realtime.service.ts): fachada con events(), listenType<T>(type), startForGroup(grupoId), stop() y connectionState$.
  2. RealtimeTransport (puerto en contract/, con el token REALTIME_TRANSPORT): permitiría cambiar SSE por otro transporte sin tocar las pantallas.
  3. FetchSseRealtimeTransport (adaptador en adapter/sse/): abre GET /api/v1/realtime/stream?grupoId=... con @microsoft/fetch-event-source, Authorization: Bearer y credentials: 'omit'. El token nunca va en la URL.

Reconexión y estados

  • Estados (RealtimeConnectionState): DISCONNECTED, CONNECTING, CONNECTED, RECONNECTING, UNAUTHORIZED y ERROR.
  • Backoff acotado: 1, 2, 5, 10 y luego 30 s como techo, más jitter aleatorio (RECONNECT_BACKOFF_MS).
  • Vigilancia de vida: el backend emite :heartbeat cada 25 s; sin actividad en 40 s (SSE_STALE_TIMEOUT_MS) el stream se considera zombi y se reabre.
  • Eventos offline y online del navegador: al caer la red se aborta la petición y se espera; al volver, se fuerza una nueva generación del bucle de conexión.
  • 401 en el stream: intenta refreshAccessToken(); si no logra renovar, pasa a UNAUTHORIZED y se detiene. 403: pasa a ERROR y se detiene.
  • onRealtimeReconnect emite cuando se pasa de RECONNECTING o ERROR a CONNECTED (no en la primera conexión). Las pantallas lo usan para pedir un único refresco HTTP y recuperar lo perdido durante el corte.

Eventos y cómo llegan a los signals

El contrato del evento es { eventId, type, occurredAt, correlationId, payload } y REALTIME_EVENT_TYPE define 21 tipos: de asistencia (ASISTENCIAS_SESION_ACTUALIZADAS, ASISTENCIAS_TOMA_ACTUALIZADAS), de tomas y QR (TOMA_ABIERTA, TOMA_CERRADA, ASISTENCIA_QR_ROTADO, ASISTENCIA_QR_REGISTRADA), de sesiones (SESION_CANCELADA, SESION_MANUAL_CREADA, SESION_SOLICITUD_CREADA, SESION_SOLICITUD_RECHAZADA), de alertas y revisiones de cancelación (ALERTA_INASISTENCIA, FALTA_SESION_AVISADA y siete REVISION_CANCELACION_*) y de catálogos (PARAMETER_UPDATED, MESSAGE_UPDATED).

Patrón típico (attendance-realtime-sync.service.ts): filtra al grupo y sesión visibles, coalesce ráfagas con auditTime(250) y emite un único «hay que refrescar». Administrador: períodos, recesos y cierre masivo

AdminPeriodosComponent (/app/admin/periodos) crea el período académico, único por institución. Al crearlo, el editor de recesos permite agregar días sin clase. Cada día se registra con POST /admin/periodos-academicos/{id}/recesos: el backend cancela las clases de ese día y avisa por correo. Si algún día falla, la pantalla lo informa en un panel de resultado. Solo un día que todavía no canceló clases puede retirarse (puedeRetirarse, DELETE .../recesos/{idReceso}). El cierre masivo está en /app/admin/sistema/cierre-masivo: es una acción real e irreversible que exige confirmación.

Sistema de diseño (tokens UCO)

La identidad visual sale del Manual de diseño institucional UCO v8.0. El archivo src/styles/uco-tokens.css contiene los colores oficiales (--uco-verde, --uco-amarillo, --uco-azul, --uco-verde-oscuro, --uco-turquesa, --uco-naranja) y las dos fuentes (Montserrat para títulos, Poppins para texto); no se edita. El bloque @theme de src/styles.css los referencia con var() y define las escalas semánticas. En AGENTS.md este sistema aparece con el nombre «Aurora Education Design System»; el documento vigente del frontend es docs/sistema-diseno-tokens.md.

Componentes compartidos y utilidades de tabla

  • superficie: utilidad que reemplaza la combinación de borde, fondo blanco y sombra de las tarjetas.
  • tabla-scroll y tabla-contenedor: marco con desplazamiento propio (alto máximo --tabla-alto-max, 70 vh) y encabezados fijos (thead th con sticky top-0 y fondo opaco). La variante tabla-scroll-libre quita el límite de alto.
  • col-acciones: deja la columna de acciones pegada al borde derecho mientras la tabla se desplaza de lado, para que los botones no queden fuera de vista. Hay col-fija y col-fija-2 para columnas fijas a la izquierda desde md.
  • tabla-tarjetas: por debajo de md (48 rem) cada fila pasa a una tarjeta apilada; el encabezado queda solo para lectores de pantalla y cada celda con data-label muestra su rótulo con ::before. Existe la variante tabla-tarjetas-compacta de dos columnas.
  • Diálogos y avisos: app-modal, app-confirm-dialog (confirmaciones irreversibles como el cierre masivo), dialogo-accesible (directiva) y ToastService (con animaciones que se desactivan con prefers-reduced-motion).

Reglas responsivas (375 px)

  • El punto de quiebre de las tablas es md (48 rem): por debajo se usan tarjetas; la tabla con tabla-tarjetas no limita el alto.
  • En pantallas táctiles o por debajo de 48 rem, los controles dentro de #contenido-principal (botones, summary, select, enlaces con inline-flex o flex) tienen al menos 2,5 rem (40 px) de alto, salvo los marcados sr-only o tap-libre.
  • La paginación pasa a «Página X de Y» compacta y botones de 44 px.
  • La auditoría de densidad (docs/ux/AUDITORIA-DENSIDAD.md) registra la comprobación a 375 px: menús dentro del viewport y scrollWidth igual a 375, sin desplazamiento horizontal de página.

Localización es-CO

  • app.config.ts registra localeEsCo con registerLocaleData y provee LOCALE_ID = 'es-CO'. Sin eso, el pipe date sale en inglés («Jan 5, 2026»).
  • Los números usan el pipe number con la coma decimal de la configuración regional, por ejemplo g.porcentajeAsistencia | number: '1.0-2' en el consolidado.
  • shared/pipes/fecha-hora.util.ts usa Intl.DateTimeFormat('es-CO', …) con la zona horaria de sesión; core/time/session-timezone.util.ts convierte entre la hora local de la sesión y los instantes UTC que viajan al backend (la API habla UTC con Z). Playwright también corre con locale: 'es-CO' y timezoneId: 'America/Bogota'.

Cómo correr los E2E con el Chrome del sistema

Los E2E (e2e/autenticacion.spec.ts, flujos-por-rol.spec.ts, guardas-de-rol.spec.ts) corren con Chromium sobre el build e2e servido por e2e/support/serve-dist.mjs. Ese servidor estático entrega dist/gestio-asistencia-frontend/browser con respaldo de SPA y sustituye /assets/env.js por e2e/support/env.e2e.js (USE_MOCKS=true, SECURITY_PROVIDER=legacy, API_URL al mismo origen). No necesitan backend, base de datos ni IdP. Cubren el login por rol, el cierre de sesión con returnUrl, los guards de rol (un rol no abre rutas ajenas) y flujos como crear un período, el seguimiento del decano, los indicadores del coordinador, la bandeja de justificaciones del docente y los reclamos del estudiante.

  1. cd GestioAsistenciaFrontend y npm ci.
  2. npm run e2e:build (equivale a ng build --configuration=e2e).
  3. npm run e2e:run. Playwright levanta node e2e/support/serve-dist.mjs 4300 (puerto 4300 por defecto, E2E_PORT lo cambia) y espera /login.
  4. El reporte HTML queda en playwright-report/; las capturas solo se guardan en las pruebas que fallan.

playwright.config.ts usa el dispositivo «Desktop Chrome» sin fijar channel, así que requiere los navegadores de Playwright instalados. En un equipo que solo tiene Google Chrome, se usa una configuración temporal fuera del repositorio que importa playwright.config.ts por ruta absoluta y fija channel: 'chrome', un testDir absoluto y el cwd del webServer en la raíz del frontend. Antes hay que compilar con --configuration=e2e (o producción, según lo que sirva serve-dist). Dato útil: tsc -p tsconfig.app.json no revisa las plantillas, por lo que un cambio de tipos que las afecte solo falla en ng build; conviene compilar antes de cerrar un cambio.

Con E2E_BASE_URL definida, Playwright no levanta servidor y apunta a ese entorno. Útil para humo sobre un despliegue, pero entonces valen los usuarios y datos reales de ese entorno, no los del simulador.

Antes de cerrar una tarea ejecuta .\AsistenciasUCO-Infra\infra.ps1 verify en la raíz del workspace (escaneo de secretos y paridad de contratos) y, dentro de GestioAsistenciaFrontend, npm run verify. No se relajan ni se desactivan pruebas para hacerlas pasar: se corrige el código de producción.

Dónde está cada cosa

Rutas en app.routes.ts, servicios HTTP en core/services, pantallas en features/<rol>.

Token solo en memoria, PKCE, roleGuard en el cliente y autoridad real en el backend.

Tiempo real

Se usa RealtimeService.listenType y se coalescen las ráfagas. Nada de setInterval.

npm run verify y los E2E. Los textos al usuario salen de mensajeUi o del backend.
