El rol de la base de datos: Smart / Thick database

Lo primero que hay que entender: en este proyecto la base de datos no es un almacén pasivo. SQL Server es la única fuente de verdad del estado (entidades, folios, catálogos) y además es quien decide: valida permisos, ventanas de tiempo, cupos, plazos y umbrales, y escribe con control transaccional explícito. El backend Spring Boot es una puerta delgada que autentica, orquesta y traduce; el frontend solo presenta.

🧠

Reglas en un solo lugar

Una regla como «el docente titular es el único que registra asistencia» se aplica dentro del procedimiento, así ningún cliente (API, script, consola SQL) puede saltársela.

⚛️

ACID donde importa

Cada comando abre su transacción (o un savepoint si ya hay una), bloquea en un orden fijo y confirma o revierte todo junto.

🧾

Contrato estable

Todos los procedimientos públicos devuelven la misma tupla; el backend la mapea sin adivinar nada del texto.

🔎

Trazabilidad

Cada llamada recibe un @idCorrelacion que viaja desde la cabecera X-Correlation-Id hasta los mensajes técnicos y la auditoría.

La tupla de resultado estándar

El contrato congelado (AsistenciasUCO-Infra/docs/contracts/db/DB_BASELINE_CONTRACT.md, sección Public SP Result) obliga a que todo procedimiento público de negocio devuelva una sola fila con cuatro columnas, en este orden exacto. Antes de la corrección del 2026-11-22, la documentación general lo resumía como «idResultado, exitoso, mensajeUsuario, mensajeTecnico»; hoy AGENTS.md usa los nombres reales de las columnas en SQL, que son:

#Columna real en SQLTipoEquivale aQué contiene
1idCorrelacionUNIQUEIDENTIFIERidResultadoEl mismo identificador de correlación recibido, para unir logs de las tres capas.
2mensajeUsuarioResultadoNVARCHARmensajeUsuarioTexto institucional listo para el usuario, tomado del catálogo CatalogoMensajeUsuario.
3mensajeTecnicoResultadoNVARCHARmensajeTecnicoDetalle técnico con el prefijo legible por máquina DBCODE=<codigo>|detalle.

Muchos comandos «extienden» la tupla agregando columnas al final (por ejemplo idToma, idSesion, totalRegistros), nunca en medio, y las dejan en NULL si estadoResultado = 0. Un ejemplo real está en el cierre de usp_registrar_asistencias_toma:

SELECT
    idCorrelacion           = @idCorrelacionDefecto,
    mensajeUsuarioResultado = @mensajeUsuarioResultado,
    mensajeTecnicoResultado = @mensajeTecnicoResultado,
    estadoResultado         = @estadoResultado,
    idToma                  = IIF(@estadoResultado = 1, @idTomaDefecto, NULL),
    totalRegistros          = IIF(@estadoResultado = 1, @totalEstudiantes, NULL);

Fuente: GestioAsistenciaDB/schema/stored-procedures/usp_registrar_asistencias_toma.sql.

DBCODE y THROW 51000: dos canales de error

El texto de cada mensaje no vive en el código sino en el catálogo. Un procedimiento pide el mensaje con usp_obtener_mensaje_catalogo @p_codigo = 'TOM_001' y recibe los dos textos ya formados. El mensaje técnico siempre empieza por DBCODE=<codigo>|:

SET @mensajeTecnicoResultado = CONCAT('DBCODE=', @codigoResultado, '|', @detalleTecnico);

Fuente: GestioAsistenciaDB/schema/stored-procedures/usp_obtener_mensaje_catalogo.sql.

Según el tipo de procedimiento, el rechazo sale por uno de dos canales:

El rechazo de negocio es un resultado, no una excepción: la fila trae estadoResultado = 0, el texto de usuario y DBCODE=.... Ejemplo: TOM_001 (toma inexistente) o SEC_002 (sin titularidad). El backend lee el DBCODE y decide el código HTTP (400, 403, 404, 409) con una tabla de clasificación; nunca interpreta frases.

Las consultas que devuelven un conjunto de filas no pueden mezclar una fila de error con datos; por eso, si la validación falla, hacen THROW 51000, @mensajeTecnicoResultado, 1;. El mensaje ya lleva DBCODE=SEC_002|... y el backend lo extrae de la excepción. Ejemplos: usp_buscar_asignaturas_paginado, usp_buscar_estudiante_por_documento_grupo (documento nulo: VAL_001; grupo ajeno: SEC_002).

Un error no previsto (deadlock, restricción violada) cae en el CATCH: el SP revierte y devuelve el código genérico SYS_001 con el detalle de ufn_obtener_detalle_error(@idCorrelacion) en el mensaje técnico. Si la transacción pertenece a un llamador externo y está en estado -1 (irrecuperable), el SP relanza con THROW; para que el dueño de la transacción la revierta.

El identificador de correlación

Todo procedimiento público recibe @idCorrelacion UNIQUEIDENTIFIER y su primer paso es usp_validar_id_correlacion_esta_presente_interno: sin correlación no se hace nada. Se concatena a los mensajes técnicos (' Correlacion: ') y se guarda en las tablas de hechos (idCorrelacionApertura, idCorrelacion en SesionSolicitud, SesionCancelacion, AuditoriaEvento.correlationId…). Así un fallo en el frontend se rastrea con una sola búsqueda hasta la fila que lo causó.

Plantilla de transacción

Todos los comandos siguen la misma plantilla: SET XACT_ABORT ON, TRY/CATCH, transacción propia o savepoint si ya hay una abierta (así el SP se puede componer dentro de otro), y reversión que solo toca lo que el propio SP abrió. Fragmento real (recortado) de usp_registrar_asistencias_toma:

SET NOCOUNT ON;
SET XACT_ABORT ON;
BEGIN TRY
    -- ...validaciones: cada una solo corre si @estadoResultado = 1...
    IF @estadoResultado = 1
    BEGIN
        IF @@TRANCOUNT = 0
        BEGIN
            BEGIN TRANSACTION;
            SET @transaccionPropia = 1;
        END
        ELSE
        BEGIN
            SAVE TRANSACTION sp_asistencias_toma;
            SET @savepointCreado = 1;
        END

        -- ...escrituras con bloqueos...

        IF @transaccionPropia = 1
        BEGIN
            IF XACT_STATE() = 1 AND (@estadoResultado = 1 OR @huboEscritura = 0)
                COMMIT TRANSACTION;
            ELSE IF XACT_STATE() <> 0
                ROLLBACK TRANSACTION;
        END
        ELSE IF @savepointCreado = 1 AND XACT_STATE() = 1 AND @estadoResultado = 0 AND @huboEscritura = 1
            ROLLBACK TRANSACTION sp_asistencias_toma;
    END
END TRY
BEGIN CATCH
    SET @estadoTransaccionCatch = XACT_STATE();
    IF @transaccionPropia = 1 AND @estadoTransaccionCatch <> 0
        ROLLBACK TRANSACTION;
    ELSE IF @savepointCreado = 1 AND @estadoTransaccionCatch = 1
        ROLLBACK TRANSACTION sp_asistencias_toma;
    IF @transaccionPropia = 0 AND @estadoTransaccionCatch = -1
        THROW;
    -- SYS_001 + ufn_obtener_detalle_error(@idCorrelacion)
    SET @estadoResultado = 0;
END CATCH

Fuente: GestioAsistenciaDB/schema/stored-procedures/usp_registrar_asistencias_toma.sql. Los rechazos previos a escribir (@huboEscritura = 0) solo confirman la transacción vacía, lo que los hace compatibles con INSERT ... EXEC.

Trampa conocida. Un SP que usa INSERT ... EXEC (como usp_generar_sesiones_grupo_v2) no puede anidarse dentro de otro INSERT ... EXEC (error 8164). Y con una transacción externa abierta, un error en el SP congelado deja XACT_STATE() = -1: solo el llamador puede revertir.

Pistas de bloqueo y orden de bloqueos

Para que dos operaciones concurrentes no se pisen, los comandos usan WITH (UPDLOCK, HOLDLOCK) al releer lo que van a modificar, siempre en el mismo orden para evitar interbloqueos: típicamente Sesion (ventana) → TomaAsistencia → TokenAsistenciaToma, y RevisionCancelacion → EstudianteGrupo.

UPDLOCK + HOLDLOCK evita que dos transacciones creen el mismo vínculo estudiante-programa:

FROM dbo.EstudiantePrograma ep WITH (UPDLOCK, HOLDLOCK)

usp_internal_asegurar_estudiante_programa_grupo.sql; la unicidad queda además protegida por UX_EstudiantePrograma_estudiante_programa.

READPAST permite que dos instancias del job de cierre automático no cierren la misma toma:

FROM dbo.TomaAsistencia t WITH (READPAST)
WHERE t.fechaCierreUtc IS NULL ...

usp_cerrar_tomas_vencidas.sql; la outbox usa UPDLOCK, READPAST, ROWLOCK en usp_reservar_notificaciones_salientes_interno.

Consultas paginadas: usp_consultar_* sobre uv_*

Toda consulta filtrada y paginada pasa por un procedimiento de consulta que lee una vista. Recibe @numeroPagina, @tamanoPagina y filtros, pagina con OFFSET ... FETCH NEXT y devuelve el total en cada fila con COUNT(1) OVER() AS totalRegistros, de donde el backend arma ApiPageResponse<T> (elementos, numeroPagina, tamanoPagina, totalElementos, totalPaginas).

EXEC dbo.usp_establecer_contexto_usuario_ejecutor @p_idUsuario = @idUsuarioDefecto;

SELECT  s.id, s.idGrupo, s.nombre, s.numero, s.fechaHoraInicio, s.fechaHoraFin,
        COUNT(1) OVER() AS totalRegistros,
        se.estaCancelada, se.codigoTipoCancelacion, se.motivoCancelacion
FROM dbo.uv_auth_sesion s
INNER JOIN dbo.uv_sesion_estado se ON se.idSesion = s.id
WHERE s.idGrupo = @idGrupoDefecto
  AND (@filtroFechaDesde IS NULL OR s.fechaHoraInicio >= @filtroFechaDesde)
  AND (@filtroSemana IS NULL OR s.numeroSemana = @filtroSemana)
ORDER BY s.fechaHoraInicio ASC, s.numero ASC, s.id ASC
OFFSET @offset ROWS
FETCH NEXT @tamano ROWS ONLY;

Fuente: GestioAsistenciaDB/schema/stored-procedures/usp_consultar_sesiones_grupo_paginado.sql. El ORDER BY incluye id como desempate para que la paginación sea determinista.

  • Tamaño máximo: el parámetro PAGINACION/TAMANO_MAXIMO acota la página; fuera de rango responde PAG_001. La validación compartida está en usp_validar_consulta_paginada_interno (correlación, ejecutor, perfil y página en un solo lugar).
  • Solo lectura: las consultas no abren transacción. El backend también puede leer directamente vistas uv_* por JPA, pero nunca tablas.
  • Orden de filtros: un filtro NULL significa «sin filtro» (@filtro IS NULL OR ...); nunca se usa un GUID vacío como centinela.

Aislamiento jerárquico dentro de los SP

La visibilidad por rol no la decide el backend ni el frontend: se fuerza dentro de la BD. Hay dos mecanismos que se combinan.

1. SESSION_CONTEXT y vistas uv_auth_*

La consulta establece SESSION_CONTEXT('idUsuarioEjecutor') con usp_establecer_contexto_usuario_ejecutor; las 13 vistas uv_auth_* filtran con ufn_obtener_usuario_ejecutor_contexto() y fallan cerradas: sin contexto devuelven 0 filas (un NULL nunca equivale a acceso total). Fragmento real de uv_auth_docente:

WHERE dbo.ufn_obtener_usuario_ejecutor_contexto() IS NOT NULL   -- fail closed
  AND (  EXISTS (SELECT 1 FROM dbo.Administrador a
                 WHERE a.usuario = dbo.ufn_obtener_usuario_ejecutor_contexto()
                   AND a.institucion = d.idInstitucion)
      OR EXISTS (SELECT 1 FROM dbo.Decano dec INNER JOIN dbo.Facultad f ON dec.id = f.decano
                 WHERE dec.usuario = dbo.ufn_obtener_usuario_ejecutor_contexto() AND f.id = d.idFacultad)
      OR EXISTS (SELECT 1 FROM dbo.Coordinador c INNER JOIN dbo.Programa pr ON c.id = pr.coordinador
                 WHERE c.usuario = dbo.ufn_obtener_usuario_ejecutor_contexto() AND pr.id = d.idPrograma)
      OR d.idUsuario = dbo.ufn_obtener_usuario_ejecutor_contexto() );

Fuente: GestioAsistenciaDB/schema/views/uv_auth_docente.sql.

El contexto es de la conexión, no de la petición. Con un pool de conexiones, un contexto que no se restaura se filtra a la siguiente petición. Por eso usp_consultar_sesiones_grupo_paginado captura el contexto previo, lo establece y siempre lo restaura (en éxito y en CATCH). Ver GestioAsistenciaDB/docs/arquitectura/DB_SESSION_CONTEXT_Y_VISTAS_AUTORIZADAS.md.

2. Titularidad jerárquica y ámbito de programas

Los comandos validan con usp_validar_titularidad_jerarquica_interno (recibe usuario, entidad padre y su tipo, por ejemplo 'SESION') y con funciones de ámbito. Por ejemplo, los programas que coordina un usuario:

Manejo del tiempo y la zona horaria

Regla de oro: todo instante se guarda en UTC (TIEMPO/ALMACENAMIENTO_INSTANTES = UTC, columnas DATETIME2 con sufijo Utc). La zona de la institución sale de parámetros: TIEMPO/ZONA_HORARIA_IANA = America/Bogota (para el backend y el frontend) y TIEMPO/ZONA_HORARIA_SQLSERVER = SA Pacific Standard Time (la que entiende AT TIME ZONE). Cuando una regla habla de «día» (festivo, receso, plazo de reclamo) se convierte primero el instante a fecha local:

AND df.fecha = CAST((s.fechaHoraInicio AT TIME ZONE 'UTC') AT TIME ZONE @zonaHorariaSqlServer AS DATE)

Fuente: GestioAsistenciaDB/schema/stored-procedures/usp_internal_aplicar_festivos_grupo.sql. El mismo patrón en ufn_calcular_fecha_limite_justificacion, que calcula el límite del reclamo en hora local y lo devuelve en UTC.

Procedencia temporal. Sesion.procedenciaTemporal marca si las horas de una sesión fueron confirmadas como UTC. Solo las sesiones con procedencia confirmada participan en festivos y recesos, y el trigger tr_Sesion_procedencia_temporal más los DENY de DML al rol runtime impiden escribir horas por fuera de los SP.

Seguridad: rol runtime y mínimo privilegio

El backend se conecta con el rol de base de datos rol_asistencias_runtime (mínimo privilegio). El modelo es deliberadamente simple: ejecuta procedimientos públicos y lee vistas, nada más.

  • Sin acceso directo a tablas: no hay SELECT sobre tablas (salvo AuditoriaEvento, donde el backend inserta). Las vistas se conceden una por una (GRANT SELECT ON dbo.uv_x), no con SELECT ON SCHEMA.
  • Sin GRANT EXECUTE ON SCHEMA::dbo: el script base hace REVOKE EXECUTE ON SCHEMA::dbo y concede procedimiento por procedimiento, derivado del inventario del código Java. Cada paquete de trabajo agrega su script (rol_asistencias_runtime_*.sql, 53 archivos, unas 166 sentencias GRANT EXECUTE y 30 DENY).
  • Fallo ruidoso: si un procedimiento requerido no existe, el script lanza THROW 52120 o 52401 con la lista de faltantes; así un SP nuevo sin permiso no pasa inadvertido (sin él, la ruta respondería 500 «EXECUTE permission was denied»).
  • Defensa en profundidad: el trigger tr_Sesion_procedencia_temporal vigila el DML directo sobre Sesion cuando el login real aún tenga privilegios de propietario.
  • Prueba del inventario: test/test_runtime_grants_backend_inventory.sql y los scripts verify_runtime_role_*.ps1.
REVOKE EXECUTE ON SCHEMA::[dbo] FROM [rol_asistencias_runtime];
GRANT EXECUTE ON [dbo].[usp_registrar_asistencias_toma] TO [rol_asistencias_runtime];  -- uno por SP
GRANT SELECT  ON [dbo].[uv_auth_sesion] TO [rol_asistencias_runtime];                    -- una por vista
DENY  EXECUTE ON [dbo].[usp_validar_sesion_operacion_interno] TO [rol_asistencias_runtime];

Patrón de GestioAsistenciaDB/schema/security/rol_asistencias_runtime.sql (los GRANT reales se generan con cursores a partir de listas; aquí se muestra la forma).

Los scripts no crean logins. Mapear el login real del backend al rol es una decisión de despliegue por ambiente. Mientras el backend use un principal sysadmin o db_owner, los DENY no le aplican y la única defensa ante DML directo es el trigger.

Convenciones de las migraciones

  • Pares up/down: NN_nombre_up.sql y NN_nombre_down.sql. Los down no los aplica migrar.ps1: la reversión es manual (ejecutar el down y borrar la fila de MigracionAplicada). Algunas pruebas verifican que un down no borre datos sin confirmación (test_pc_migracion_37_down_sin_confirmacion.sql).
  • Numeración: 01 a 04 son cargas iniciales anteriores al esquema por objeto; las administradas empiezan en la 05. Hay 71 versiones (la 35 no existe). Se ordena por versión y luego por nombre.
  • Marcadores: cada migración tiene en migrar-marcadores.json un efecto propio que sigue vigente (tabla, columna, índice, restricción, objeto o fila) para que Detectar sepa si ya se aplicó.
  • Idempotencia: las migraciones se escriben para poder repetirse; los cuerpos de vistas y SP se despliegan con deploy_schema.ps1 (CREATE OR ALTER) y la migración solo toca lo que CREATE OR ALTER no puede (tablas, columnas, datos, restricciones).

Congelación WORM y supersesión

El contrato público de la BD está congelado bajo el principio WORM (escribir una vez, leer muchas) en AsistenciasUCO-Infra/docs/contracts/db/: DB_BASELINE_CONTRACT.md con su .sha256, DB_DEVELOP_FREEZE_ADDENDUM.md y DB_DEVELOP_FREEZE_MANIFEST.sha256. El manifiesto lista los archivos congelados con su SHA-256 (calculado con CRLF normalizado a LF, para que sea idéntico en Windows y Linux).

ManifiestoQué registra
DB_DEVELOP_FREEZE_MANIFEST.sha256La línea base congelada (DB-GP-001C). Se genera solo tras una decisión autorizada.
DB_UTC_D06_POST_FREEZE_MANIFEST.sha256Extensiones posteriores al congelamiento, con dos formas de línea: SUPERSEDES <hash-original> (un archivo congelado que cambió por un work item aprobado) y WORK_ITEM (archivo nuevo).
DB_CULM001_D_POST_FREEZE_MANIFEST.sha256Archivos del paquete D (solo líneas WORK_ITEM), actualizados con freeze-manifest.ps1 -Mode UpdateCulm001D.
DB_LB004D_SUPPORT_BINDING_MANIFEST.sha256Archivos del vínculo de soportes de reclamos.

La verificación (.\scripts\freeze-manifest.ps1 -Mode Verify, id GOLDEN_PATH_FREEZE_MANIFEST_VERIFIED dentro del gate) acepta el nuevo hash de un archivo congelado solo si la línea de supersesión nombra el hash exacto original. Así los SP congelados (por ejemplo usp_generar_sesiones_grupo) no cambian en silencio: la evolución se hace creando _v2 y dejando el original intacto.

Regla de contrato. Toda modificación de un contrato exige formalización previa, actualización del hash y verificación cruzada de repositorios. Nunca se «acomoda» la base para que el backend o el frontend compilen; si la forma difiere, se reconstruye desde el contrato.
