# LB-001D.2 — DECISIONES

## D-1 Sin default funcional (TD-051)
`@Value("${app.security.azure-events.webhook-token:}")` y `application.yml` con `${AZURE_EVENTGRID_WEBHOOK_TOKEN:}`. Vacío/ausente/en blanco ⇒ el filtro responde 401 antes de procesar. No se movió el default a otro archivo ni se desactiva el filtro. Se mantuvo `@Value` (no se creó una clase de properties: ampliaría el alcance).

## D-2 Header único (TD-052)
Solo `aeg-sas-token`. Eliminado `getParameter("token")`; ningún query parameter se lee. Event Grid real no fue consultado en esta fase, pero no existe fuente autoritativa en el repositorio que exija query token, por lo que no hay `CONTRACT/OPERATIONAL_CONFLICT`.

## D-3 Comparación segura
Se comparan digests SHA-256 con `java.security.MessageDigest.isEqual` (tiempo constante en el JDK). El hash previo iguala longitudes y evita filtrar longitud/contenido por timing. Sin dependencias nuevas. `trim()` se conserva (comportamiento AS-IS) tanto para la credencial configurada como para el header.

## D-4 Path matching
Riesgo AS-IS: `endsWith("/api/v1/internal/azure-events")` intercepta y exime de CSRF rutas ajenas como `/x/api/v1/internal/azure-events`. Decisión: coincidencia exacta de `requestURI` menos `contextPath` (`AzureEventGridAuthFilter.isWebhookRequest`), reutilizada por el matcher CSRF. El context path legítimo sigue soportado (test). La regla de autorización usa `AzureEventGridAuthFilter.WEBHOOK_PATH` (misma cadena).

## D-5 `permitAll` != sin autenticación
`.requestMatchers(WEBHOOK_PATH).permitAll()` solo evita exigir el JWT de negocio en `AuthorizationFilter`; la autenticación la ejecuta obligatoriamente `AzureEventGridAuthFilter`, registrado antes de `BearerTokenAuthenticationFilter`. `/api/v1/**` sigue autenticado. La exclusión CSRF se mantiene porque Event Grid no envía Bearer/CSRF; se prueba que sin credencial sigue 401 (no un bypass).

## D-6 Logging
El filtro no registra nada. El controller solo registra `eventType`/`subject` (sin credencial ni payload completo); sin cambios. `SECRET_EXPOSURE = 0`.

## D-7 Separación de tres alcances de build
| Alcance | Comando | Contenido |
|---|---|---|
| Normal | `.\mvnw.cmd verify` | Surefire: unit/component/architecture/contracts; JaCoCo |
| SQL Server | `.\mvnw.cmd -Pintegration verify` | Failsafe `**/*IT.java` excepto `*CloudIntegrationIT` |
| Azure Cloud | `.\mvnw.cmd -Pazure-integration verify` | Failsafe solo `**/*CloudIntegrationIT.java`; Surefire y JaCoCo desactivados en este perfil |

Justificación de omitir Surefire/JaCoCo en `azure-integration`: se pidió ejecutar únicamente la integración Azure; el gate de cobertura del perfil no tiene sentido con solo una IT. El aislamiento es por clasificación/perfil, sin `@Disabled`, `assume*` ni `catch`/return.

## D-8 Ambiente de la Cloud IT
`AzureCloudIntegrationIT` lee `AZURE_KEYVAULT_ENDPOINT`/`AZURE_APPCONFIG_ENDPOINT` (env o `-D`); si faltan, **falla** con mensaje explícito. Se eliminaron los endpoints hardcodeados de la prueba. Sigue con `DefaultAzureCredential`; no hay secretos en código. Es solo lectura. Observación no modificada: `CatalogAdapterConfigurationTest` usa un hostname de App Configuration como literal en un test de wiring que no realiza lecturas (no es cloud).
