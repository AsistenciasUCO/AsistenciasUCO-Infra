El resultado anterior reportó CVEs críticos/altos en dependencias Java; **necesitan validación individual contra SARIF y advisory oficial**, no se declaran explotables por presencia de versión.

## Orden recomendado (no cambiar 15 dependencias a ciegas)
1. Descargar SARIF original y registrar ruleId CVE, severidad en fuente, paquete Maven/OS, versión instalada, versión fixed (si existe), target/imagen, evidencia de uso, estado y responsable.
2. Clasificar origen: **Boot BOM/transitivo**, dependencia declarada en `pom.xml`, base `eclipse-temurin:25-jre-alpine` o paquete dev/build. Distinguir stage final Docker de imagen build.
3. Confrontar CVE con advisory vendor. Ejemplo documentable de revisión: `spring-webmvc 7.0.7` cae en rama afectada `7.0.0–7.0.8` de CVE-2026-47884 y el vendor recomienda >=7.0.9, **pero la explotación requiere condiciones como XsltView y rutas wildcard**. Véase https://spring.io/security/cve-2026-47884/ . Verificar si se usa `XsltView`; no afirmar RCE real sin evidencia.
4. Validar vía Maven `help:effective-pom` y `dependency:tree` y preferir upgrade de Spring Boot patch compatible/BOM a versiones corregidas. Sin override arbitrario de Spring MVC/Hibernate/Tomcat. Mantener Java 25 y controlar cambios de APIs.
5. Para Tomcat/Netty/Bouncy Castle, registrar todos los CVEs y fixedVersions de SARIF e inspeccionar quién los introduce: `dependency:tree`, `mvn dependency:analyze` si aplica. Confirmar que Tomcat embedded está expuesto y si Netty/BC participan en rutas en runtime.
6. Red / regression: unit + ArchUnit + OpenAPI + tests JWT/seguridad + MinIO/ClamAV/SQL Server IT relevantes; construir **nueva** imagen del SHA y rerun ambos Trivy. Conservar results antes/después; no cerrar por subir versiones sin rescaneo.
7. Definir política tras inventario: HIGH/CRITICAL fixable en runtime => remediation con prioridad; sin fix/exposición compensada => decisión y fecha de revisión. Adoptar fail-on sólo tras baseline/false positive evaluados; evitar `ignore-unfixed` global o exclusions cosméticas.
