## Análisis AS-IS de configuración

- `application.yml`: `asistencia-query-provider: ${APP_ADAPTERS_PERSISTENCE_ASISTENCIA_QUERY_PROVIDER:jdbc}`.
- Existen `application-local.yml` y `application-dev.yml` (solo `asistencias.swagger-ui.enabled`); **no** existe `application-prod.yml`. `docker-compose.yml` usa `SPRING_PROFILES_ACTIVE=default`. `.env` local no fija perfil ni provider.

## Decisión de política (ambientes)

| Ambiente | Provider efectivo | Mecanismo |
|---|---|---|
| perfil `local` | **jpa** | `application-local.yml` (`${ENV:jpa}`) |
| perfil `dev` | **jpa** | `application-dev.yml` (`${ENV:jpa}`) |
| sin perfil / `default` / prod-like | **jdbc** (sin cambio) | `application.yml` |
| rollback en cualquier ambiente | jdbc | `APP_ADAPTERS_PERSISTENCE_ASISTENCIA_QUERY_PROVIDER=jdbc` (la variable gana al perfil) |

Motivo: no existe separación prod explícita; cambiar el default global equivaldría a una decisión de despliegue no autorizada. `.env.example` deja de fijar `=jdbc` (lo anularía el perfil); queda comentado con la política.

## Alcance / no alcance

Cambia: `application-local.yml`, `application-dev.yml`, `.env.example`, test `AsistenciaQueryProviderActivationTest`, documentación. **No cambia**: Application (puertos/use cases), Domain, controllers, DTOs, OpenAPI, DB, frontend, commands (siguen JDBC), Composition Root (1 único `AsistenciaRepositoryPort`, ya existente), seguridad, realtime.

## Riesgos y rollback

- Riesgo: JPA regresa datos distintos → mitigado por paridad LB-002.1 + E2E HTTP con lectura/escritura/relectura.
- Rollback: variable de entorno a `jdbc` (validado), o revertir los dos yml.
