## Error semantics

- El result set público (`idCorrelacion, mensajeUsuarioResultado, mensajeTecnicoResultado, estadoResultado`) es la única señal estructurada garantizada por el contrato DB congelado (M-18, MATCH).
- Ningún literal de código formal (`SEC_*/ATT_*/SES_*/RC_*/GEN_*/EST_*`) aparece como señal de clasificación en `DbFailureClassifier`/`DbExceptionTranslator` (M-19).
- 8 de 11 códigos relevantes del Golden Path (`SEC_001, SEC_002, ATT_001, ATT_002, ATT_003, SES_003, SES_004, GEN_002`) no tienen ninguna rama de clasificación hoy y caerían en `ERR_DB_UNCLASSIFIED` → HTTP 500, violando directamente `TASK_AUTORIZADA.md` §17 ("No devolver 500") para el caso RBAC/titularidad.
- 3 códigos (`SES_001, RC_001, EST_004`) sí producen el HTTP/código esperado hoy, pero por coincidencia de texto libre con patrones ya construidos para otros dominios (`Usuario/Grupo/Docente`), no por lectura de un código de catálogo — confirmado por los comentarios de `DbExceptionTranslatorTest.java` ("texto verificado en vivo").
- Conclusión formal, conforme a `TASK_AUTORIZADA.md` §18: **NO existe señal determinista suficiente en el contrato DB congelado** para mapear estos códigos de forma garantizada. Se declara `CONTRACT_CONFLICT` para esta porción exacta del alcance (mapeo de errores `SEC_*/ATT_*/SES_003/SES_004/GEN_002`; `SES_001/RC_001/EST_004` quedan en estado intermedio: funcionan hoy pero sin contrato que lo garantice — ver Decisiones/Bloqueos). No se inventa una heurística nueva de texto libre como solución (`TASK_AUTORIZADA.md` §18, última línea).

## Transacción/atomicidad

- Batch de asistencia: "Validar todo antes de escribir... Escritura atómica e idempotente... Concurrente sobre la misma sesión/estudiante termina en una sola cabecera y un solo detalle" — invariante DB-side, el backend NO revalida estas reglas (`registrarAsistenciasSesion` solo serializa y llama al SP, sin lógica de atomicidad propia). **MATCH** con `TASK_AUTORIZADA.md` §15 ("DB se encarga de invariantes definitivas... Backend puede validar estructura tempranamente, pero NO debe definir una semántica distinta").
- Sesion: `numero`/`codigo` con `UPDLOCK, HOLDLOCK` — invariante DB-side, sin réplica de lógica de concurrencia en el backend (confirmado, no hay `@Transactional` ni locks JVM en los adapters de Sesion revisados). **MATCH**.

## Tiempo/UTC
